# `hc mount` — Design Doc

## Purpose

Extend `hc` (hermes-cli) to manage systemd mount units the same way it currently manages Docker Compose services: definitions live in the `hermes` registry, `hc` applies them to hosts, and `hc` can report their status. This covers MergerFS pool mounts and the bind mounts that expose subsets of the pool to individual services (Jellyfin, Tdarr, etc.), including dependency ordering between them.

## Background / Motivation

Atlantis is being set up with a MergerFS pool (`/mnt/pool`) built from three HDDs, no parity. Individual services (Jellyfin, Tdarr, future *arr apps) will reach into the pool via systemd bind mounts under `/srv/<service>/`, each depending on `mnt-pool.mount` being active first. Hand-writing and tracking these unit files per host doesn't fit the existing Hermes model, where compose configs are already registry-managed and host-applied via `hc`. Mounts should follow the same pattern.

## Scope decision: which mounts `hc` manages

Not every mount in the topology goes through the registry. Split:

- **Storage pools (`mnt-pool`, or however many a host has — a host may have more than one MergerFS pool, e.g. across different disk sets): left in `/etc/fstab`, unmanaged by `hc`.** Each is the root of its own dependency tree, changes rarely (only when a disk is added/removed from that pool), and keeping them boring/manual limits the blast radius if `hc` ever has a sync bug — a mistake in the tool can't take out actual storage, only the derivative bind mounts. Note that fstab entries are still turned into systemd mount units automatically by `systemd-fstab-generator`, so `hc mount status` reads a pool's `.mount` unit like any other unit regardless of where its definition came from, and `Requires=` on it works from other units the same way either way.

  `hc` still needs to know each pool's name and mount point, though — to validate `depends_on`, to list it in `hc mount status`, and to include it in the docker.service drop-in's `After=`/`Requires=`. That's declared in an optional `<host>/pools.yml` at the registry root (a sibling of `mounts/`, not inside it — it's metadata about units `hc` does *not* render, not a mount spec):

  ```yaml
  # hermes/atlantis/pools.yml
  pools:
    - name: mnt-pool
      target: /mnt/pool
    - name: mnt-pool2
      target: /mnt/pool2
  ```

  A host with a single pool still declares it here (one entry); a host with none omits the file entirely. `hc mount sync` rejects a `mounts/*.yml` spec whose `name` collides with a declared pool — same reasoning as before, just generalized to N pools instead of one hardcoded name.
- **Per-service bind mounts (`srv-jellyfin-media`, `srv-tdarr-media`, etc.): registry-managed via `hc mount sync`/`enable`/`disable`.** These churn as services are added, and are exactly what benefits from the sync/apply/status workflow.

## Docker startup ordering

Containers shouldn't start before their backing mounts are live, and this needs to be reliable at boot, not racy. Two options were considered:

- **Per-compose-stack wrapper unit** (`jellyfin-compose.service` with `After=`/`Requires=` on its specific mount) — more granular, but requires `restart: "no"` on the containers themselves or Docker's own crash-restart behavior can bypass the wrapper, and reimplementing crash-recovery at the systemd layer is more machinery than it's worth.
- **Single drop-in on `docker.service` itself, blocking the whole daemon until all registered mounts are active** — chosen approach. Docker becomes unable to start before its storage foundation exists, the same way it already implicitly depends on `/var/lib/docker`'s filesystem being present; this isn't a special case, it's the same category of dependency. Docker's own `restart: unless-stopped` crash-recovery behavior stays intact for the actual "container crashed, host didn't reboot" case, since the daemon being up already implies the mount was up when it started.

This keeps systemd/mounts as the substrate Docker sits on rather than something Docker actively waits on and reasons about — a wrapper, not a driver.

### The drop-in

```ini
# /etc/systemd/system/docker.service.d/wait-for-mounts.conf
# Managed by hc — do not edit directly. Regenerated by `hc mount sync`.
[Unit]
After=mnt-pool.mount srv-jellyfin-media.mount srv-tdarr-media.mount
Requires=mnt-pool.mount srv-jellyfin-media.mount srv-tdarr-media.mount
```

One file, not one per mount — there's no independent lifecycle to preserve at this layer (unlike the mount units themselves, which do need to stay separate since they're enabled/disabled/checked independently). This is a derived aggregate of "every mount currently registered for this host," so it collapses naturally to a single list.

### Keeping it current: full regeneration, not incremental edits

`hc mount sync` is the *only* thing that writes this file. As the last step of every sync run, after processing all `mounts/*.yml` specs for the host:

1. Collect the systemd unit name for every mount spec just processed, plus every pool declared in `pools.yml` — those aren't registry-managed but are always a dependency Docker should wait on.
2. Rewrite the drop-in's `After=`/`Requires=` lines from that full list — full overwrite, never an append or incremental diff.
3. Run `systemctl daemon-reload` automatically (cheap, safe, no running-container impact).
4. If the drop-in's content actually changed versus the previous version, print a notice rather than restarting Docker automatically: `drop-in updated, restart docker to apply: hc mount sync --restart-docker`. Restarting `docker.service` bounces every container on the host, so that step stays gated behind an explicit flag rather than happening implicitly.

Because the file is fully regenerated from the registry state every time, adding a new `mounts/srv-radarr-media.yml` spec means it's present in the drop-in on the very next `hc mount sync`, with no manual editing step. The "do not edit directly" header is load-bearing — any manual edit to this file is expected to be clobbered on the next sync and should be treated as a sign the change belongs in the registry instead.

### Staleness check

`hc mount status` (or a dedicated `hc mount check`) should compare the drop-in file currently on disk against what the registry says it *should* contain, and flag a mismatch. This catches two drift scenarios: someone hand-edited the drop-in directly, or the registry was updated but `hc mount sync` was never actually run on this particular host.

## Registry structure

```
hermes/
└── <host>/
    ├── compose/
    │   └── jellyfin.yml
    ├── pools.yml                 # optional — names/mount points of fstab-managed pools (see above)
    └── mounts/
        └── srv-jellyfin-media.yml
```

Each file under `mounts/` is a declarative spec, not a raw systemd unit — `hc` generates the unit file from it. One file per mount. `pools.yml`, by contrast, declares units `hc` never renders — see the "Scope decision" section above for its schema. `hc mount sync` rejects any `mounts/*.yml` whose `name` collides with an entry in `pools.yml`.

## Mount spec schema

```yaml
name: srv-jellyfin-media       # required, used as unit name (<name>.mount)
source: /mnt/pool/media        # required, "What="
target: /srv/jellyfin/media    # required, "Where="
type: bind                     # optional, default "bind"; also supports fuse.mergerfs, ext4, etc.
options: []                    # optional, list of mount options (e.g. mergerfs branch opts)
depends_on: mnt-pool           # optional — name of another registered mount, OR a pool declared in
                                # pools.yml (e.g. mnt-pool, mnt-pool2)
description: "Jellyfin media bind mount"  # optional, used in unit's Description= and in status output
```

## Generated systemd unit

`hc mount sync` renders each spec into `/etc/systemd/system/<name>.mount`. Example output for `srv-jellyfin-media.yml`:

```ini
# Managed by hc — do not edit directly. Source: hermes/atlantis/mounts/srv-jellyfin-media.yml
[Unit]
Description=Jellyfin media bind mount
After=mnt-pool.mount
Requires=mnt-pool.mount

[Mount]
What=/mnt/pool/media
Where=/srv/jellyfin/media
Type=bind
Options=bind

[Install]
WantedBy=multi-user.target
```

`depends_on: mnt-pool` maps to `After=` and `Requires=` on `mnt-pool.mount`. If `depends_on` is absent, those lines are omitted (used for the root pool mount itself).

Note the systemd naming convention: the unit filename must match the mount point path (with `/` replaced by `-`), *or* the `Where=` value inside the unit must match the filename. `hc` should derive the unit filename from `target`, not from `name`, to satisfy systemd's requirement — `name` is a friendly identifier used in the registry and in `hc` output, but the actual file on disk should be named per systemd's path-escaping rule (e.g. `srv-jellyfin-media.mount` for `/srv/jellyfin/media`, generated via `systemd-escape --path --suffix=mount <target>`). Flag this explicitly in implementation — getting it wrong causes the unit to silently fail to bind to the mount point.

## Subcommands

### `hc mount sync`
- Fetches mount specs from the registry (same SFTP/git-based mechanism as compose sync).
- Renders each spec to a systemd unit file in `/etc/systemd/system/`.
- Runs `systemctl daemon-reload`.
- Does **not** automatically enable/start new units — surfaces a diff of added/changed/removed units and requires `hc mount enable <name>` (or `--apply` flag) to activate, consistent with treating mount changes as higher-risk than compose changes.

### `hc mount enable <name>`
- `systemctl enable --now <unit>`.
- Refuses to enable a mount whose `depends_on` target isn't itself active, with a clear error rather than letting systemd fail silently.

### `hc mount disable <name>`
- `systemctl disable --now <unit>`.
- Warns (doesn't block) if other registered mounts declare `depends_on` on this one.

### `hc mount status [name]`
- No argument: table of all mounts registered for the current host.
- With argument: single-mount detail view.

Per-mount status pulls from three sources:

1. `systemctl show <unit> -p ActiveState,SubState,LoadState,UnitFileState --value` — systemd's view.
2. `findmnt --json <target>` — ground truth on whether the path is actually mounted; catches drift where systemd thinks a mount is active but it's been unmounted outside systemd's tracking.
3. `df -h --output=avail,pcent <target>` — free space, since these are storage mounts and it's the thing most likely to be checked alongside status.

Table view:

```
NAME                     STATE    MOUNTED  DEPENDS_ON      FREE     USE%
mnt-pool                 active   yes      -               3.1T     78%
srv-jellyfin-media       active   yes      mnt-pool        3.1T     78%
srv-tdarr-media          failed   no       mnt-pool        -        -
```

`STATE` reflects systemd's ActiveState. `MOUNTED` reflects the independent `findmnt` check — a mismatch between the two (STATE=active, MOUNTED=no) should be visually flagged (e.g. color/warning marker) since it indicates the mount was torn down outside systemd's control.

Detail view (`hc mount status srv-tdarr-media`) additionally shows: `journalctl -u <unit> -n 20 --no-pager` tail, so a failed mount's cause is visible without a separate command.

## Compose integration (follow-on, not in initial scope)

Once mounts are tracked, `hc` can optionally verify a service's required mounts are active before `docker compose up`. This would need compose specs to declare a `requires_mounts: [srv-jellyfin-media]` field. Noting here as a natural next step; not required for the initial mount-management feature.

## Open questions for implementation

1. Where does `hc` get the current host's identity to know which `mounts/` subdirectory to sync from? (Presumably same mechanism compose sync already uses — confirm and reuse.)
2. Should `hc mount sync` refuse to remove a unit file for a mount that's currently active and mounted, without an explicit `--force` or prior `disable`? (Recommend yes, to avoid accidentally unmounting live storage via a registry change.)
3. Output formatting — reuse whatever table/color library the existing compose status output uses, for visual consistency.

## Out of scope

- Automatic rebalancing or data movement between pool drives.
- MergerFS pool creation itself (formatting drives, initial branch setup) — this doc covers only the ongoing management of already-created mounts via `hc`.
- SnapRAID or any parity layer (not in use for this pool).
